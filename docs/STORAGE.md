# ArchivePass native storage and custody

Upkeep principal and operations are separate accounting concepts. Initialization's pre-transferred native balance funds operations. `fund_upkeep` accepts entirely restricted principal; `fund_operations` accepts entirely operational funds. Exact-one-yocto security deposits are separately counted. Direct native transfers are unallocated operational surplus and do not create donor credit. No operational surplus is owner-withdrawable.

The current bounded implementation serializes at most 256 commitments, eight provider configurations, nine fixed credit rows and one latest payment attempt per creditor/kind. It stores no archive bytes or growing event vector. Endpoints are capped256 ASCII bytes, labels80 UTF-8 bytes, account IDs64 bytes, hashes32 bytes represented as64 hex characters. The native worst-case-state test constructs maximum-length records, terminal challenge summaries, credits, payment summaries and a transfer lock, then checks serialized application state against a conservative **260,000-byte application-state allowance**. On5November2026 the constructed stress fixture serialized to **192,293 bytes**, leaving67,707bytes in the application allowance. The fixture has maximum commitment/provider/payment/lock string lengths; manifest/policy retain the ordinary vector metadata, so the allowance also deliberately covers their small bounded extra growth. This is a native Borsh size measurement, not receipt-level worst-case gas evidence.

The actual optimized primary WASM is259,651bytes, SHA-256 `1978b1c8049dc89fc00757f7724efa715bd36d97bd6b7b26903fbdb8083abc94`. Receiver fixture is113,561bytes, SHA-256 `9b5b010ae85bb4e4b4159021e868b8083e2ba1cfec7fde1473e2864f95dc224c`. Built with Rust1.99.1 GNU / SDK5.30 / cargo-near0.22, `cargo near build non-reproducible-wasm --no-abi` (postprocessed wasm-opt). These are actual artifact hashes, not a claim of byte reproducibility across independent toolchains. A6.5NEAR testnet operational endowment is expected to cover code+reservedstate at the current storage price; the actual initialized `get_storage_quote` is authoritative.

At initialization, `storage_budget_bytes = env::storage_usage() + 260000`; initialization storage includes the deployed account/code baseline. Every successful storage-growing public mutation verifies both serialized application state <=260000 and actual storage usage <= the fixed budget. Required operational balance is that budget times the runtime's actual storage byte cost. `get_storage_quote` exposes exact budget, actual usage, serialized application size and required operational yoctoNEAR. This deliberately reserves future capacity up front rather than letting sponsorship subsidize growing state. Deployment must supply enough operational balance before initialization, typically several faucet NEAR depending on the final WASM.

Every public mutation also requires account balance to cover that operational requirement plus all **nonpending** principal liabilities: available upkeep + nonterminal reservations + available provider/refund credits. Pending native transfers may already have left the account before their callback; they remain in gross ledger conservation and are not falsely represented as cash still present. Before scheduling a new payout, the claimant's full credit is included in the pre-claim coverage check. Ownership changes cannot redirect any bucket. Small private callbacks settle a pre-funded fixed record and intentionally do not require new operational funding before releasing a failed/successful attempt.

At every transition:

`principal_in = available + reserved + available_provider_credit + available_refund_credit + pending + principal_paid`.

Reserved is independently rebuilt from nonterminal commitments and paid from fixed creditor rows. No saturating arithmetic masks drift. Arithmetic is checked u128/u64. At expiry, all commitments must be terminal before the single unused-reserve sweep, preventing late releases from becoming stranded. Earned or pending provider claims remain payable after expiry.

A fresh atomic create+transfer+deploy+initialize batch can omit AddKey. The contract itself has no upgrade/add-key/delete-account method. Actual empty access-key-list verification is a deployment evidence gate; this document does not claim it has been achieved. If a deployment retains a full-access key, its deployer can replace the code or move funds and the application/README must say so.

The contract can be audited independently from SQLite. App/keeper SQLite backup, migrations, blob directories and local recovery belong in BACKEND/OPERATIONS documentation. Pending chain callbacks must never be cleared based on elapsed time or a local server switch.
